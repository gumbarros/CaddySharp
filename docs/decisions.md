# MVP decisions

- Caddy v2.11.7 and DNNE 2.1.2 are pinned. Go/cgo called the minimal `caddysharp_probe` export on Linux x64 with .NET SDK 10.0.112 and runtime 10.0.12. It returned `0x43534801` after `try_preload_runtime() = 0`.
- Go uses `dlopen` for the DNNE library and `dlsym` for exports. The C/Go layer does not implement a separate hostfxr loader. DNNE uses the runtimeconfig adjacent to its exporter; the configured `runtime_config` must point to that same file. Changing it requires a restart.
- The bridge invokes the application's normal `Main` entry point. Apps reference `CaddySharp` and call `builder.Host.UseCaddyServer()` after creating the builder. The extension receives a process-local configuration delegate from the DNNE-loaded copy of the same assembly through `AppContext` and adds the Caddy-backed `IServer` and host lifetime. The delegate is absent during a direct launch, so Kestrel remains the server. The handoff is needed because DNNE and the app load separate copies of the managed bridge assembly.
- `IHostingStartup` alone does not solve this for `WebApplicationBuilder`: Kestrel registers its server after the hosting startup callback, so its `IServer` takes precedence. ASP.NET also cannot probe the DNNE bridge assembly from its isolated native bridge directory without extra assembly loading setup.
- Requests and responses are buffered. Go copies data into C-owned memory and releases it after the export returns; the export copies the body into managed memory. The Go side polls `caddysharp_is_completed` and calls the blocking wait only after completion. The GCHandle is released only after completion, including after cancellation.
- True streaming needs a versioned chunk or pipe ABI. Caddy's current handler API and the existing `cs_bytes` contract do not expose a compatible push/pull boundary, so body limits remain bounded buffering rather than streaming backpressure.
- The launcher disables Go signal-based asynchronous preemption and sets `GOMAXPROCS=1`; the handler bounds simultaneous ABI waits to 32. Without these safeguards, sustained mixed Go/CoreCLR load reproduced scheduler and split-stack crashes. The stable configuration completed 60-second mixed runs at 64 clients with zero errors and zero pending handles.
- A compatible reload reuses the runtime when the configuration signature matches. Application or runtime changes are rejected; CoreCLR is not unloaded.
